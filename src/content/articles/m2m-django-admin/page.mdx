Django's default handling of many-to-many (`ManyToManyField`) relationships in the admin can be frustrating. By default, it renders a standard multiple-select box, which quickly becomes unusable as your database grows. And if you use third-party packages like `django-waffle` with generic models, you can end up with poor related names and clunky queries.

In this post, we'll look at how to improve this experience by explicitly defining your relations and configuring the admin with modern DX patterns.

## Explicit Many-to-Many Relations

By default, `django-waffle` provides an `AbstractUserFlag` class to subclass:

```python
from waffle.models import AbstractUserFlag

class Flag(AbstractUserFlag):
    # 'users' and 'projects' are handled internally by Waffle
    pass
```

While this sets up automatic relations, it locks you into Django's default reverse names (like `flag_set`).

We can improve both our queries and our code readability by explicitly redefining the relationships on our model:

```python
from django.db import models
from waffle.models import AbstractUserFlag

class Flag(AbstractUserFlag):
    users = models.ManyToManyField(
        'auth.User',
        related_name='flags',  # Now user.flags.all() works
        blank=True,
    )

    projects = models.ManyToManyField(
        'common.Project',
        related_name='flags',  # Now project.flags.all() works
        blank=True,
    )
```

This redefinition allows using the cleaner `user.flags.all()` and `project.flags.all()` ORM syntaxes.

## Traceable SQL Queries

Defining explicit relationship names also makes our SQL queries much cleaner and easier to read when debugging or profiling.

For example, when using the generic auto-generated name, the join path in the query is harder to scan:

```sql
SELECT * FROM "waffle_flag"
INNER JOIN "waffle_flag_users" ON ("waffle_flag"."id" = "waffle_flag_users"."flag_id")
WHERE "waffle_flag_users"."user_id" = 1;
```

By defining `related_name='flags'` explicitly, Django generates a clean, traceable pathway:

```sql
SELECT * FROM "common_flag"
INNER JOIN "common_flag_users" ON ("common_flag"."id" = "common_flag_users"."flag_id")
WHERE "common_flag_users"."user_id" = 1;
```

This is a huge help when inspecting query logs or using profiling tools.

## Upgrading the Admin UI

The default Django admin interface for Many-to-Many fields is a vertical multiple-select box. This requires holding down Control (or Command) to select multiple items, and lists all records in a single block.

For small relations, you can upgrade this to a searchable, two-column widget using `filter_horizontal`:

```python
from django.contrib import admin

class FlagAdmin(admin.ModelAdmin):
    # Replaces the multiple-select with a dual-box selector
    filter_horizontal = ('users', 'projects')
```

For larger datasets, where loading all users into the page is too slow, you should use `autocomplete_fields`. This uses Select2 to load choices via an AJAX request as the user types:

```python
class FlagAdmin(admin.ModelAdmin):
    # Enables AJAX-backed search as you type
    autocomplete_fields = ('users', 'projects')
```

_Note: To use `autocomplete_fields`, the related models (`User` and `Project` in this case) must have `search_fields` defined in their respective `ModelAdmin` classes._

## Summary

Explicitly defining Many-to-Many relations and configuring `filter_horizontal` or `autocomplete_fields` is a quick win for your Django projects. It improves code readability, streamlines SQL debugging, and makes the admin interface much more user-friendly.
