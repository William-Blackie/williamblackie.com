I have been spending time in the Django admin recently, and the default
many-to-many widget keeps catching my eye for the wrong reasons. Whether
it is feature flags, project membership, or permission trees, the default
render is usually a list of raw IDs or a giant, unmanageable select box.
It feels like a database tool wearing the mask of an admin interface.

This is a short note on the two changes that have made the biggest
difference for me: being explicit about the reverse relationship in the
model, and switching the admin to widgets that respect how people
actually scan a screen.

## The problem

When you link `User` or `Project` to a Waffle `Flag`, the default admin
behaviour is a vertical select, or a raw ID field if you are unlucky.
The result is the same either way:

- **No context.** You see an ID, not a name.
- **Search tax.** Finding the right record means going elsewhere,
  copying an ID, and pasting it back.
- **Visual noise.** Tabular inlines become unreadable once you have
  more than a handful of rows.

It is the kind of friction that gets quietly accepted because the model
works, until someone on the team starts avoiding the admin entirely.

## Make the model say what it means

The first fix is on the model side. Waffle’s `AbstractUserFlag` defines
the M2M relationships for you, which is convenient, but it locks you
into generic reverse names like `flag_set` that read poorly in queries
and even worse in code:

```python
from waffle.models import AbstractUserFlag

class Flag(AbstractUserFlag):
    # 'users' and 'projects' are handled internally by Waffle
    pass
```

Re-declaring the fields lets you take back the relationship name and the
SQL it produces:

```python
from django.db import models
from waffle.models import AbstractUserFlag

class Flag(AbstractUserFlag):
    users = models.ManyToManyField(
        'auth.User',
        related_name='flags',  # user.flags.all() now reads cleanly
        blank=True,
    )

    projects = models.ManyToManyField(
        'common.Project',
        related_name='flags',  # project.flags.all() too
        blank=True,
    )
```

The model is the same shape, but the queries get clearer, and the admin
inherits a more honest name for the relation.

## Pick widgets that respect how people read

The second fix is to swap the default widget for something that does
searching and selection in one place:

```python
class FlagAdmin(admin.ModelAdmin):
    # Searchable dual-box for picking related rows.
    filter_horizontal = ('users', 'projects')

    # AJAX-backed search for the long lists.
    autocomplete_fields = ('users', 'projects')
```

`filter_horizontal` removes the raw-ID scan and adds a filter box.
`autocomplete_fields` adds a search-ahead picker for the lists that are
too long for a dual box. Both are stock Django; nothing here is custom.

## A small change, a quieter admin

Neither change is novel on its own. Together they turn the admin from a
database dump into something a non-engineer can use without a translator.
That is usually the difference between an admin that gets used and one
that gets worked around.
