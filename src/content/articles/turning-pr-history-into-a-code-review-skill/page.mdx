Every mature open-source project or scaling engineering team suffers from the same cognitive drain: **"drive-by" pull requests**. These are contributions that superficially look good and pass basic test suites, but violate deep, subtle codebase conventions and architectural invariants.

The result is that maintainers spend vast amounts of cognitive energy repeating the same review feedback: warning against database signal bypasses, flagging silent caching regressions, or correcting database-specific query quirks.

What if we stopped treating AI as a passive autocomplete helper, and instead treated it as an **adversarial review shield**?

By extracting years of historical pull request discussion history and compiling it into a deterministic, local review skill, we can build a protective first-pass filter. Much like a local, repository-specific **CodeRabbit**, this adversarial shield automatically intercepts and pushes back against sub-optimal code _before_ a human maintainer ever has to waste time looking at the patch.

The tool I built to test this concept is [code-review-skill-creator](https://github.com/William-Blackie/code-review-skill-creator) (accompanying [slides here](https://github.com/William-Blackie/code-review-skill-creator/blob/main/slides.md)).

## The Core Concept: Defending Codebase Invariants

Instead of using an LLM to blindly summarize a source tree, we analyze the actual conversations maintainers had about what was acceptable to merge. This treats historical PR comments not just as feedback, but as a **supervision signal** for quality.

We structure this adversarial review skill around four semantic concepts:

- **Distributional**: Review comments represent how a team actually defines quality in their codebase.
- **Directive**: PR feedback consists of explicit constraints and code rules, not just observations.
- **Diachronic**: Project habits and standards evolve over time, meaning chronology matters.
- **Conflict Resolution**: Deterministic authority weights and recency resolve rule overlaps when reviewers disagree.

## Building the Pipeline

The pipeline is composed of lightweight, highly inspectable Python scripts:

- `extract_prs.py`: Pulls merged pull requests and inline reviews from the GitHub GraphQL API.
- `rank_authors.py`: Calculates reviewer authority weights based on active contribution and review counts.
- `process_data.py`: Sorts pull requests chronologically and injects reviewer weights.
- `run_synthesis.py`: Processes batch synthesis using an LLM.
- `merge_rules.py`: Applies deterministic precedence logic to resolve rule conflicts.
- `split_standards.py`: Generates the final Markdown skill and standard files.

## Extracting Local Context

In `extract_prs.py`, instead of ingesting entire code files, we extract the comment, the file path, and the review thread's `diffHunk` block:

```python
comments.append(
    {
        "body": comment.get("body", ""),
        "path": comment.get("path"),
        "diff_hunk": comment.get("diffHunk"),
        "created_at": comment.get("createdAt"),
    }
)
```

This ensures the pipeline receives exactly the local code context necessary to understand the exact constraint the reviewer was enforcing.

## Reviewer Authority and Precedence

Rather than letting the LLM guess which guidelines take precedence, we compute reviewer authority weights in Python and apply a deterministic merge policy:

```python
if nr["authority_weight"] < existing["authority_weight"]:
    crs["rules"][topic_slug] = nr
elif nr["authority_weight"] == existing["authority_weight"]:
    if nr["batch_num"] >= existing["batch_num"]:
        crs["rules"][topic_slug] = nr
```

By programmatically favoring the feedback of senior maintainers or newer batches, we make sure that as the project's architecture evolves, the automated review skill adapts accordingly.

## Why Chronological Batching Matters

Summarizing years of pull requests in one massive prompt loses the chronological context of coding style changes.

By dividing the review history into chronological batches, we preserve newer norms without ignoring historical context. Smaller batches are also cheaper to run and easier to debug.

## Side-by-Side: Human Review vs. Automated Review Skill

To see the real-world value of this approach, let's look at how the generated skill performs when faced with a newly opened pull request, compared to a manual human code review using an actual Django repository constraint.

### The Scenario: Mixing TextField & SQL IN Lookups on Oracle

In Django's ORM, `TextField` columns map to `NCLOB` (National Character Large Object) datatypes on the Oracle database backend. Oracle imposes strict limitations on `LOB` fields: standard comparison operators (like `=`) and lookup clauses (like `IN`) are explicitly forbidden on `LOB` columns in SQL query predicates.

A contributor submits a pull request expanding the Django lookup test suite, adding a test case that filters a model using an `IN` operator on a `TextField` column.

#### The Code Change (PR Diff):

```diff
# In tests/lookup/tests.py
 class LookupTests(TestCase):
+    def test_in_lookup_in_filter_text_field(self):
+        self.assertSequenceEqual(
+            Season.objects.filter(
+                In(F("nulled_text_field"), [F("nulled_text_field"), "special_value"])
+            ),
+            [self.s2],
+        )
```

#### 1. The Human Review

During the manual code review on GitHub, **Mariusz Felisiak (`@felixxm`)**, Django's lead ORM maintainer, reviews the PR and leaves the following feedback:

- The issue is found only _after_ the contributor has pushed their changes and requested a review, causing a delay cycle in CI.

### The Takeaway

Automating code review guidelines is not about replacing human reviewers. It is about capturing their institutional knowledge—often lost in years of PR history—and making it active.

Rather than using generative AI to write more code faster, we can use it to build a robust defense layer. An adversarial review skill acts as an automated first-pass reviewer, ensuring that the hard-earned lessons of your senior maintainers are active on every single commit. Maintainers no longer have to spend cognitive energy catching recurring mistakes; the adversarial shield pushes back on the rubbish, leaving humans to focus on the architecture.

## Summary

Extracting code review standards from historical PR discussions provides an inspectable, repository-specific review skill. It is far more useful than a generic style guide because it is grounded in the real constraints your team enforces.
